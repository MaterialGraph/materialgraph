# MG-AUD-093

Title

Public validation accepts nonexistent chemical symbols

Status

✅ Resolved

Resolution Version

Post-v1.9.18

Affected Components

- Canonical periodic-table domain data
- Shared discovery element-filter dependency
- Seven discovery GET routes
- `avoid_element` and `prefer_element` query parameters
- Domain and API regression tests

Root Cause

Public discovery routes applied only string-length constraints to element
filters. Structurally valid but nonexistent symbols could therefore enter
discovery processing. The database could not serve as the validator because
its element table contains only the subset currently represented by imported
MaterialGraph data, not the full periodic table.

Resolution

✓ Added a centralized catalogue of all 118 recognized chemical element
symbols.

✓ Added canonical symbol normalization, including conventional casing and
surrounding-whitespace normalization.

✓ Added one shared FastAPI dependency that validates and normalizes both
element-filter parameters.

✓ Applied the dependency consistently to candidates, chains, graph, subgraph,
path, connected-community, and modularity-community routes.

✓ Preserved the distinction between chemical legitimacy and dataset coverage:
a valid symbol such as `Cu` is accepted even when no current material record
uses it, while an unknown symbol such as `Xx` returns `422`.

Regression Verification

✓ Domain tests verify that the catalogue contains exactly 118 symbols,
including `H` and `Og`, and that every canonical symbol normalizes to itself.

✓ Domain tests verify mixed-case normalization, surrounding-whitespace
normalization, and rejection of nonexistent symbols.

✓ API regressions cover all seven affected routes and both element-filter
parameters.

✓ The focused tests, full regression suite, and Ruff checks passed.

API Contract

Yes. Nonexistent chemical symbols now receive `422`, and accepted symbols are
normalized before reaching discovery services. Valid symbols are not rejected
merely because MaterialGraph has no current dataset coverage for them.

Database Migration

No.

Scientific Impact

Invalid element-filter requests can no longer influence discovery results.
No scoring, ranking, graph, or pathway algorithm changed. This remediation
validates symbol identity only; it does not claim that MaterialGraph contains
research data for every recognized element.

Lessons Learned

Chemical-domain validity and current database coverage are separate concerns
and require separate representations. A partial research dataset must not be
used as the authority for the existence of chemical elements.

# MG-AUD-060

Title

Pending graph-job claiming is not concurrency-safe

Status

✅ Resolved

Resolution Version

Post-v1.9.18

Affected Components

- `GraphJobService.claim_next_pending_job()`
- PostgreSQL graph-job claim transactions
- Multi-worker graph-job execution
- Graph-job service integration tests
- Isolated PostgreSQL test-database procedure

Root Cause

The service selected the oldest `PENDING` job and changed it to `RUNNING`
without locking the selected row. Two workers could therefore read the same
pending row before either transaction committed, allowing duplicate execution.

Resolution

✓ Added `FOR UPDATE SKIP LOCKED` to pending-job selection.

✓ Restricted selection to `PENDING` jobs and retained a one-row claim limit.

✓ Added a stable final job-ID tie-breaker after creation time so equal-time
claims remain deterministic.

✓ Changed the selected job to `RUNNING`, recorded its start time, and committed
the claim transaction before returning the job to a worker.

Regression Verification

✓ PostgreSQL integration coverage verifies that a locked oldest job is skipped
and the next eligible pending job is claimed.

✓ PostgreSQL integration coverage verifies that no job is returned when the
only pending job is locked by another transaction.

✓ Service regressions verify that a claimed `RUNNING` job is not claimed again,
that two pending jobs are claimed in deterministic oldest-first order, and
that no-pending-job behavior returns `None`.

✓ The focused graph-job tests and the full regression suite passed against the
isolated PostgreSQL database `materialgraph_test`.

Test-Database Safety Evidence

The temporary Windows Command Prompt `DATABASE_URL` override was verified
before migrations, seeding, and tests:

```cmd
py -c "from app.core.database import engine; print(engine.url.database)"
```

The deterministic reference baseline was restored and verified before the
full suite:

```text
materials: 28
material 5: (5, 'mp-19017', 'LiFePO4')
```

After testing, the temporary override must be removed in the same Command
Prompt so normal `.env` configuration becomes authoritative again:

```cmd
set DATABASE_URL=
```

The effective database must be verified before any subsequent migration,
seeding, development, or deployment operation. Credentials and complete
connection strings are not recorded in audit documents.

API Contract

No public API schema change. Internally, concurrent workers now receive
distinct claimable jobs instead of being able to claim the same pending row.

Database Migration

No schema change was required for concurrency-safe claiming.

During isolated test-database reconstruction, downgrading the graph-job
migration left the PostgreSQL `job_status` enum behind, causing the next
upgrade to fail until the orphaned type was removed. This migration downgrade
hygiene issue is not part of the MG-AUD-060 concurrency defect and remains an
explicit follow-up.

Scientific Impact

No scientific score, ranking, graph, pathway, or evidence semantic changed.
The remediation prevents duplicate execution of the same queued graph job
under concurrent workers.

Scope Boundary

MG-AUD-060 closes atomic pending-job claiming only. `complete_job()` and
`fail_job()` still permit contradictory lifecycle transitions and remain
tracked under MG-AUD-061.

Lessons Learned

Queue correctness must be verified on the production database dialect with
independent concurrent transactions. A passing single-session state-transition
test does not establish atomic multi-worker claiming.

# MG-AUD-061

Title

Graph-job lifecycle permits contradictory state transitions

Status

✅ Resolved

Resolution Version

Post-v1.9.18

Affected Components

- `GraphJobService.complete_job()`
- `GraphJobService.fail_job()`
- PostgreSQL terminal-state transition transactions
- Graph-job lifecycle and concurrency tests
- Isolated PostgreSQL test-database procedure

Root Cause

Terminal update methods loaded a job by ID and then overwrote its status
without requiring the persisted current state to be `RUNNING`. Pending jobs,
already completed jobs, and already failed jobs could therefore be moved
directly or contradictorily into another terminal state. A read-then-check
implementation would also leave competing completion and failure transactions
vulnerable to a race.

Resolution

✓ Replaced unconditional terminal mutations with atomic conditional updates
that match both the job ID and `status = RUNNING`.

✓ Restricted successful lifecycle transitions to `RUNNING -> COMPLETED` and
`RUNNING -> FAILED`.

✓ Made invalid, repeated, contradictory, and missing-job transitions return
`None` without changing persisted state.

✓ Used one transition timestamp for both `completed_at` and `updated_at`.

Regression Verification

✓ Service tests verify successful completion and failure only after a job has
been claimed and changed to `RUNNING`.

✓ Regressions verify rejection from `PENDING`, rejection after `COMPLETED` and
`FAILED`, repeated terminal attempts, unknown job IDs, and timestamp equality.

✓ A PostgreSQL concurrency test runs competing completion and failure attempts
and verifies that exactly one atomic terminal transition succeeds.

✓ The full regression suite passed with 545 tests.

✓ Ruff checks passed for `app/services/graph_job_service.py` and
`tests/services/test_graph_job_service.py`.

Test-Database Safety Evidence

The verification ran against the isolated PostgreSQL database
`materialgraph_test`. After testing, the temporary Windows Command Prompt
override was removed, and the effective normal database was explicitly
verified as `materialgraph`. Credentials and complete connection strings are
not recorded in audit documents.

API Contract

No public API schema changed. The internal service contract now returns an
updated `GraphJob` only when an atomic transition from `RUNNING` succeeds and
returns `None` for missing jobs or invalid current states.

Database Migration

No schema migration was required for lifecycle enforcement. The previously
observed downgrade issue that leaves the PostgreSQL `job_status` enum behind is
separate from MG-AUD-061 and remains an explicit migration-hygiene follow-up.

Scientific Impact

No scientific score, ranking, graph, pathway, or evidence semantic changed.
Persisted job status can no longer be overwritten by a contradictory or
out-of-order terminal transition.

Lessons Learned

Lifecycle validation must be part of the database mutation predicate. A
service-level read followed by a status check is insufficient when competing
workers can attempt different terminal outcomes concurrently.

# MG-AUD-063

Status

✅ Resolved

Resolution Version

Post-v1.9.18

Affected Components

- `MaterialNeighborhoodService.get_neighborhood()`
- Limited neighborhood node and edge selection
- Neighborhood graph-closure regression tests

Root Cause

The neighborhood service independently truncated its deterministically sorted
node and edge collections. An edge could survive its own limit even when one
of its endpoint nodes had been removed by the node limit, producing a dangling
source or target reference in the response.

Resolution

✓ Kept the existing deterministic node ordering and node limit.

✓ Built the returned node-ID set from the limited nodes.

✓ Filtered edges so both `source_material_id` and `target_material_id` must be
present in the returned node-ID set before applying the edge limit.

✓ Preserved accurate `node_count` and `edge_count` values from the returned
collections.

Regression Verification

✓ Four focused service tests verify that restrictive limits cannot produce
dangling edges, `limit=1` returns only the root and no edges, a sufficiently
large limit retains all eligible edges, and response counts match collection
lengths.

✓ The full regression suite passed with 549 tests.

✓ Ruff passed for `app/services/material/neighborhood_service.py` and
`tests/services/material/test_neighborhood_service.py`.

Test-Database Safety Evidence

Verification ran against the isolated PostgreSQL database
`materialgraph_test`. The normal local development database remains separate
and is not a pytest target.

API Contract

No public schema changed. Limited neighborhood responses now enforce the
existing graph-closure expectation: every returned edge references two nodes
present in the same response.

Scientific Impact

No scientific score, ranking, pathway, or evidence semantic changed. The
returned neighborhood topology is now internally valid after response limits
are applied.

Lessons Learned

Graph node and edge limits cannot be applied independently. Edge selection
must be constrained by the final returned node set.

# MG-AUD-071

Status

✅ Resolved

Resolution Version

Post-v1.9.18

Affected Components

- `MaterialSimilarityService.get_similar_materials()`
- Similarity criticality loading
- Similarity-service regression tests

Root Cause

The similarity service loaded criticality separately for the source material
and each limited candidate. Its request-local cache avoided duplicate lookups
but did not prevent query count from growing with the number of distinct
candidates.

Resolution

✓ Selected the limited candidate set before loading criticality.

✓ Bulk-loaded criticality once for the source material and all limited
candidate material IDs through `get_material_criticality_bulk()`.

✓ Reused the bulk result map while calculating candidate criticality deltas,
directions, explanations, and ranking keys.

✓ Preserved `None` for unknown criticality and retained existing deterministic
ranking semantics.

Regression Verification

✓ Sixteen focused similarity-service tests passed, including regression
coverage that verifies exactly one bulk call for the source and limited
candidates, no single-material criticality calls, and preserved unknown-value
semantics.

✓ The full regression suite passed with 551 tests.

✓ Ruff passed for `app/services/material/similarity_service.py` and
`tests/services/material/test_similarity_service.py`.

API Contract

No public schema or response semantic changed. Similarity results retain their
existing scores, criticality fields, explanations, and deterministic ordering.

Database Migration

No.

Scientific Impact

No scientific score, ranking policy, or evidence semantic changed. The
remediation reduces database query amplification only.

Lessons Learned

Request-local caching prevents duplicate work but does not eliminate N+1 query
growth across distinct candidates. Candidate-dependent evidence should be
loaded in bulk after the bounded candidate set is known.
